# implement 技能报告

## 第一部分：技能内容详细总结

### 一、技能概述

`implement` 是 Matt Pocock 技能体系中主构建链的**执行步骤**，位于倒数第二步。它的职责是将已经确定的工作（spec、tickets 或对话中刚刚达成的计划）转化为代码并提交。该技能的独特之处在于：它**绝不重新讨论计划**——没有访谈、没有澄清回合、不提出替代方案。上游确定的方案就是输入，技能的全部工作就是将其转化为一次提交。

主构建链中的位置：

```
grill-with-docs → to-spec → to-tickets → implement → code-review
```

### 二、一次运行的五个步骤

每次调用按照以下顺序执行：

1. **阅读工单或规格**并确定接缝（seams）。
2. **在预定的接缝上驱动 TDD**（测试驱动开发），每次一个红-绿切片（red-green slice）。
3. **频繁进行类型检查**，并逐个运行单个测试文件。
4. **在末尾运行一次完整测试套件**。
5. **运行 code-review**，然后提交到当前分支。

一次运行覆盖一个工单。`to-tickets` 产出的工单被设计为垂直切片，每个切片的大小适配一个全新的上下文窗口，因此预期的节奏是：清除上下文、实现一个工单、提交、再次清除。每个工单是自包含的，这使得前一个工单的上下文是可以丢弃的。

### 三、预定接缝（Pre-agreed Seams）

接缝（seam）是该技能运行的核心概念：即在不触及内部实现的前提下观察行为的公共边界。测试存在于接缝之上。在编写任何代码之前就在接缝上达成一致，是保持测试持久性的关键——因为底层的实现可以在测试不变的情况下被重写。

"预定"（pre-agreed）一词承载了真正的分量，但也是该技能最薄弱的环节：

- `implement` 内部没有任何东西负责"约定"接缝。
- `tdd` 是负责询问的技能，它在未确认的接缝上拒绝编写测试。
- 在实践中，协议要么在上游的 spec 中达成，要么在运行时的第一次交互中达成。
- 如果协议从未发生，前置条件永远不会触发，运行就会悄然变成"直接写代码"。

### 四、使用场景与选择

该技能为用户调用型（`disable-model-invocation: true`），Agent 不会自动触发，其他技能也不能调用它。

| 工作当前的状态 | 应选择的技能 |
|-------------|------------|
| 追踪器上的工单 | `/implement #42`，每个会话一个工单 |
| 一份 spec，尚未拆分，构建跨多个会话 | 先用 `to-tickets`，然后逐个 `/implement` |
| 一份 spec，且构建规模较小 | 直接对 spec 使用 `/implement` |
| 仅存在于刚刚的对话中，且规模仍小 | 在同一窗口中直接 `/implement` |
| 尚未写成任何形式 | 先用 `grill-with-docs` 或 `grill-me` |
| 一个确定的、想要测试先行的行为，无需 spec | 直接用 `tdd` |
| 已构建完成，需要检查 | 直接用 `code-review` |

### 五、已知问题与注意事项

1. **不会关闭工单**：技能在提交后结束，绝不触碰工作项，也不处理 `code-review` 的发现、不打勾验收标准复选框。用户需要手动关闭工单和核对标准。

2. **不支持并行**：一次调用，一个工单。多个 `/implement` 会话在同一工作目录中并行运行是危险的——它们共享同一个工作目录、同一个索引和同一个 HEAD，可能导致提交相互覆盖、stash 消失等问题。

3. **无法打开 PR**：技能直接提交到当前分支，没有配置开关或 PR 模式。用户可在调用时覆盖指令。

4. **code-review 可能看不到变更**：`code-review` 审查的是 `git diff <fixed-point>...HEAD`，不包含暂存区和工作区的变更。`implement` 在提交前运行它，因此如果尚未有中间提交，diff 中就没有可审查的内容。

5. **工单可能太大**：一次非平凡的运行消耗 100k+ token 是正常的。杠杆在上游——在 `to-tickets` 中确定合适的工单大小。

6. **工单引用歧义**：`/implement #2` 在一个新的会话中，Agent 可能会将其解析为它能看到的任何编号列表，而非配置的追踪器。建议传递完整引用或 URL。

### 六、工作判定标准

技能正常工作的标志：

- 会话开始时读取工单或规格，并重述它将构建的内容，而非询问你要构建什么。
- 在实际追踪中可以看到真正的 `/tdd` 调用，而非仅仅是 diff 中出现测试。
- 类型检查和单个测试文件在运行期间反复执行，完整套件在接近尾声时运行一次。
- 运行到达提交步骤，无需你提示继续。
- diff 是一个工单的变更量：一个贯穿所有层的垂直切片，而非多个工单混在一起。
