# Engineering Triage Skill -- 详细分析报告

---

# 第一部分：中文详细总结

## 一、Skill 目的与核心功能

Triage 技能用于在项目 Issue 追踪器上，将 Issue 和外部 PR 按照一个精简的角色状态机进行流转。整个流程涵盖：分类（categorize）、验证（verify）、必要时进行深度追问（grill），并最终为可交由 Agent 执行的条目撰写 Agent Brief。该技能旨在将维护者从重复性的 Issue 分诊工作中解放出来，同时确保每个待处理条目在移交给自动化 Agent 之前具备足够清晰、完整、可执行的规格说明。

---

## 二、角色体系

### 2.1 分类角色（Category Roles）

每个经过分诊的 Issue 必须恰好携带一个分类角色：

- **`bug`**：某功能已损坏，表现为不符合预期的行为
- **`enhancement`**：新功能或对现有功能的改进请求

### 2.2 状态角色（State Roles）

每个经过分诊的 Issue 必须恰好携带一个状态角色，共五种：

- **`needs-triage`**：维护者需要对其进行评估
- **`needs-info`**：等待报告者提供更多信息
- **`ready-for-agent`**：规范已完整，可交由 AFK Agent 执行
- **`ready-for-human`**：需要人工实现（涉及判断、外部访问、设计决策或手工测试等无法委托的场景）
- **`wontfix`**：不会执行

### 2.3 状态流转规则

未标记的 Issue 通常首先进入 `needs-triage`，从那里可流转至 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。`needs-info` 在报告者回复后返回 `needs-triage`。维护者可随时覆盖任何状态；遇到不寻常的状态转换时应标记并确认。

### 2.4 角色冲突处理

如果某个 Issue 上存在冲突的状态角色，技能应将其标记出来，并在执行任何操作前征求维护者意见。

### 2.5 规范角色名与标签映射

上述为规范角色名（canonical role names）。实际 Issue 追踪器中使用的标签字符串可能有所不同，映射关系应由系统预先提供。

---

## 三、PR 支持

PR 被视为带有附加代码的 Issue，使用完全相同的角色、状态和状态机。关键差异点：

- `ready-for-agent` 对 PR 而言意味着：已附加 Agent Brief，Agent 应对当前 diff 采取下一步行动
- `ready-for-human` 对 PR 而言意味着：已准备好由人工进行合并
- 外部 PR（根据追踪器配置定义"外部"）会被包含在需要关注的分桶中，每条标注 `[PR]` 或 `[issue]`
- 协作者（collaborator）的进行中 PR 不属于分诊工作范围（此过滤仅用于发现阶段；被明确指定的 PR 总是会被分诊，不论作者身份）

---

## 四、免责声明要求

每次分诊过程中在 Issue 追踪器上发布的**每一条评论**都必须以以下免责声明开头：

```
> *This was generated by AI during triage.*
```

---

## 五、调用模式（Invocation Modes）

维护者通过 `/triage` 命令调用，并用自然语言描述需求。支持以下模式：

### 5.1 展示需要关注的条目

查询 Issue 追踪器，按三个分桶呈现，每桶内按最早优先排列：

1. **未标记（Unlabeled）**：从未被分诊过的条目
2. **`needs-triage`**：评估进行中的条目
3. **`needs-info` 且有报告者活动**：自上次分诊笔记以来报告者已有回复的条目

每个分桶显示数量和每个条目的一行摘要，供维护者选择。

### 5.2 分诊特定 Issue 或 PR

对指定的 Issue/PR 执行完整的分诊流程（见第六节）。

### 5.3 快速状态覆盖（Quick State Override）

如果维护者说"把 #42 移到 ready-for-agent"，则直接信任并应用该角色。确认即将执行的操作（角色变更、评论、关闭），然后执行。跳过追问（grilling）环节。如果移动到 `ready-for-agent` 且未经过追问环节，应询问是否需要编写 Agent Brief。

### 5.4 恢复之前的会话

如果 Issue 或 PR 上存在先前的分诊笔记，读取它们，检查报告者是否已回答了任何待处理问题，在继续之前呈现更新后的全貌。不要重复询问已解决的问题。

## 六、分诊工作流（Triage Workflow）

### 步骤 1：收集上下文（Gather Context）

- 阅读完整的 Issue 或 PR（正文、评论、标签、作者、日期；对于 PR，还需阅读 diff）
- 解析先前的分诊笔记，避免重复询问已解决的问题
- 使用项目的领域词汇表探索代码库，尊重相关区域的 ADR（架构决策记录）
- 执行两项代码库检查：
  - **（a）冗余检查**：按领域概念（而非仅按请求措辞）搜索所请求行为的现有实现，报告搜索范围。如果找到，则属于"已实现"的 `wontfix`（进入步骤 5 处理）
  - **（b）先前拒绝检查**：读取 `.out-of-scope/*.md` 中的所有文件，找出与该请求相似的任何先前拒绝记录

### 步骤 2：推荐（Recommend）

向维护者提出分类和状态建议及理由，附上与请求相关的代码库摘要（包括是否已实现）。等待维护者指示。

### 步骤 3：验证声明（Verify the Claim）

在追问之前，检查声明是否成立：
- 对于 bug：按报告者的步骤尝试复现
- 对于 PR：确认 diff 是否如其声称的那样工作，检出代码，运行相关测试或命令
- 报告结果：确认（附代码路径）、失败、或信息不足（这是强 `needs-info` 信号）
- 确认的验证能产生更有力的 Agent Brief

### 步骤 4：追问（Grill，如需要）

如果请求需要充实细节，调用两个技能："grilling"（追问）和"domain-modeling"（领域建模），每次一轮问题地进行深度追问，在决策落地时同步更新 `CONTEXT.md` / ADR。

### 步骤 5：应用结果（Apply the Outcome）

- **`ready-for-agent`**：发布 Agent Brief 评论（参见 AGENT-BRIEF.md）
- **`ready-for-human`**：与 Agent Brief 结构相同，但注明为何无法委托（判断决策、外部访问、设计决策、手工测试等）
- **`needs-info`**：发布分诊笔记（使用下方模板）
- **`wontfix`**：关闭 Issue，评论内容取决于原因：
  - **已实现**：变更已存在于代码库中，指出其位置；**不**写入 `.out-of-scope/`（该知识库仅用于被拒绝的请求，不用于已构建的功能）
  - **被拒绝（bug）**：给出礼貌的解释，然后关闭
  - **被拒绝（enhancement）**：写入 `.out-of-scope/`，在评论中链接，然后关闭
- **`needs-triage`**：应用角色。如有部分进度可附加评论。

### Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

在追问过程中确认的所有内容都应记录在"已确认的内容"下，避免工作成果丢失。问题必须具体且可操作，不能是"请提供更多信息"这种模糊表述。

## 七、Agent Brief 编写原则

Agent Brief 是当 Issue/PR 移动到 `ready-for-agent` 时发布的结构化评论。它是 AFK Agent 工作的权威规格说明。原始正文和讨论是上下文，Agent Brief 是契约。

### 7.1 持久性优先于精确性（Durability over Precision）

Issue 可能在 `ready-for-agent` 状态停留数天甚至数周，期间代码库会发生变化。编写 Brief 时需确保其在文件被重命名、移动或重构后仍然有用。

- **应该做**：描述接口、类型和行为契约；命名 Agent 应查找或修改的具体类型、函数签名或配置结构
- **不应做**：引用文件路径（会过时）；引用行号；假设当前实现结构将保持不变

### 7.2 行为描述而非过程描述（Behavioral, not Procedural）

描述系统**应该做什么**，而非**如何实现**。Agent 将重新探索代码库并做出自己的实现决策。

- **好的描述**："`SkillConfig` 类型应接受一个可选的 `schedule` 字段，类型为 `CronExpression`"
- **坏的描述**："打开 src/types/skill.ts，在第 42 行添加 schedule 字段"

### 7.3 完整的验收标准（Complete Acceptance Criteria）

Agent 需要知道何时完成。每个 Agent Brief 必须包含具体、可测试的验收标准，每项标准应可独立验证。

### 7.4 明确的范围边界（Explicit Scope Boundaries）

明确说明不在范围内的内容，防止 Agent 过度设计或对相邻功能做出假设。

### 7.5 Agent Brief 模板

```markdown
## Agent Brief

**Category:** bug / enhancement
**Summary:** one-line description of what needs to happen

**Current behavior:**
Describe what happens now. For bugs, this is the broken behavior.
For enhancements, this is the status quo the feature builds on.

**Desired behavior:**
Describe what should happen after the agent's work is complete.
Be specific about edge cases and error conditions.

**Key interfaces:**
- `TypeName`: what needs to change and why
- `functionName()` return type: what it currently returns vs what it should return
- Config shape: any new configuration options needed

**Acceptance criteria:**
- [ ] Specific, testable criterion 1
- [ ] Specific, testable criterion 2
- [ ] Specific, testable criterion 3

**Out of scope:**
- Thing that should NOT be changed or addressed in this issue
- Adjacent feature that might seem related but is separate
```

## 八、Out-of-Scope 知识库

`.out-of-scope/` 目录存储被拒绝的功能请求的持久记录，服务于两个目的：

1. **机构记忆**：记录功能被拒绝的原因，使推理不会随 Issue 关闭而丢失
2. **去重**：当新 Issue 到来并匹配之前的拒绝记录时，技能可以呈现之前的决策，避免重复讨论

### 8.1 目录结构

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

每个**概念**一个文件，而非每个 Issue 一个文件。请求同一功能的多个 Issue 归入同一文件。

### 8.2 何时检查

在分诊的步骤 1（收集上下文）中，读取 `.out-of-scope/` 中的所有文件。按概念相似度而非关键词匹配（如"night theme"匹配 `dark-mode.md`）。匹配时告知维护者："这与 `.out-of-scope/dark-mode.md` 类似。我们之前因 [原因] 拒绝了此请求。您仍然持相同看法吗？"

### 8.3 何时写入

仅在 **enhancement**（非 bug）被**拒绝**为 `wontfix` 时写入。此规则同样适用于 enhancement PR。**不要**在因"已实现"而关闭为 `wontfix` 时写入，那会导致去重检查出现误判。

### 8.4 文件格式

文件应以轻松可读的风格编写，更接近简短设计文档而非数据库条目。使用段落、代码示例和示例来使推理清晰有用。应包含：概念标题、为何超出范围的实质性理由（引用项目范围/哲学、技术约束或战略决策）、以及先前请求列表。

### 8.5 维护者选项

遇到匹配时，维护者可选择：
- **确认**：将新 Issue 添加到现有文件的"先前请求"列表，然后关闭
- **重新考虑**：删除或更新 out-of-scope 文件，Issue 进入正常分诊流程
- **不认同**：Issue 虽相关但不同，进入正常分诊流程

### 8.6 更新或删除

如果维护者对先前拒绝的概念改变主意：
- 删除 `.out-of-scope/` 文件
- 无需重新打开旧 Issue（它们是历史记录）
- 触发重新考虑的新 Issue 进入正常分诊流程

> 2. **推荐。** 向维护者提出分类和状态建议及理由，附上与请求相关的代码库简要总结（包括是否已实现）。等待指示。

---

<!--原文-->
> 3. **Verify the claim.** Before any grilling, check that the claim holds up. For a bug, reproduce it from the reporter's steps. For a PR, confirm the diff does what it claims: check it out, run the relevant tests or commands. Report what happened: confirmed (with code path), failed, or insufficient detail (a strong `needs-info` signal). A confirmed verification makes a much stronger agent brief.

<!--翻译-->
> 3. **验证声明。** 在任何追问之前，检查声明是否成立。对于 bug，按报告者的步骤复现。对于 PR，确认 diff 是否如其声称的那样工作：检出代码，运行相关测试或命令。报告结果：已确认（附代码路径）、失败、或信息不足（强 `needs-info` 信号）。得到确认的验证能产生更有力的 Agent Brief。

---

<!--原文-->
> 4. **Grill (if needed).** If the request needs fleshing out, call the Skill tool twice, for "grilling" and "domain-modeling", and grill it into shape a round of questions at a time, sharpening domain terms and updating `CONTEXT.md`/ADRs inline as decisions land.

<!--翻译-->
> 4. **追问（如需要）。** 如果请求需要充实细节，调用 Skill 工具两次，分别为"grilling"和"domain-modeling"，每次一轮问题地进行深度追问，在决策落地时内联更新 `CONTEXT.md`/ADR，同时打磨领域术语。

---

<!--原文-->
> 5. **Apply the outcome:**
>    - `ready-for-agent`: post an agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
>    - `ready-for-human`: same structure as an agent brief, but note why it can't be delegated (judgment calls, external access, design decisions, manual testing).
>    - `needs-info`: post triage notes (template below).
>    - For `wontfix`, close the issue, with the comment depending on *why*:
>      - **Already implemented**: the change already exists in the codebase. Point to where it lives; do **not** write to `.out-of-scope/` (that KB is for *rejected* requests, not built ones).
>      - **Rejected (bug)**: give a polite explanation, then close.
>      - **Rejected (enhancement)**: write to `.out-of-scope/`, link to it from a comment, then close ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
>    - `needs-triage`: apply the role. Optional comment if there's partial progress.

<!--翻译-->
> 5. **应用结果：**
>    - `ready-for-agent`：发布 Agent Brief 评论（参见 AGENT-BRIEF.md）。
>    - `ready-for-human`：与 Agent Brief 结构相同，但注明为何无法委托（判断决策、外部访问、设计决策、手工测试）。
>    - `needs-info`：发布分诊笔记（模板见下方）。
>    - 对于 `wontfix`，关闭 Issue，评论取决于*原因*：
>      - **已实现**：变更已存在于代码库中。指出其位置；**不要**写入 `.out-of-scope/`（该知识库用于*被拒绝*的请求，而非已构建的请求）。
>      - **被拒绝（bug）**：给出礼貌的解释，然后关闭。
>      - **被拒绝（enhancement）**：写入 `.out-of-scope/`，在评论中链接，然后关闭（参见 OUT-OF-SCOPE.md）。
>    - `needs-triage`：应用角色。如有部分进度可附加评论。

## OUT-OF-SCOPE.md 原文与翻译

---

<!--原文-->
> # Out-of-Scope Knowledge Base
> 
> The `.out-of-scope/` directory in a repo stores persistent records of rejected feature requests. It serves two purposes:
> 
> 1. **Institutional memory**: why a feature was rejected, so the reasoning isn't lost when the issue is closed
> 2. **Deduplication**: when a new issue comes in that matches a prior rejection, the skill can surface the previous decision instead of re-litigating it

<!--翻译-->
> # Out-of-Scope 知识库
>
> 仓库中的 `.out-of-scope/` 目录存储被拒绝的功能请求的持久记录。它服务于两个目的：
>
> 1. **机构记忆**：记录功能被拒绝的原因，使推理不会随 Issue 关闭而丢失
> 2. **去重**：当新 Issue 到来并匹配之前的拒绝记录时，技能可以呈现之前的决策，避免重复争论

---

<!--原文-->
> ## Directory structure
> 
> ```
> .out-of-scope/
> ├── dark-mode.md
> ├── plugin-system.md
> └── graphql-api.md
> ```
> 
> One file per **concept**, not per issue. Multiple issues requesting the same thing are grouped under one file.

<!--翻译-->
> ## 目录结构
>
> ```
> .out-of-scope/
> ├── dark-mode.md
> ├── plugin-system.md
> └── graphql-api.md
> ```
>
> 每个**概念**一个文件，而非每个 Issue 一个文件。请求同一功能的多个 Issue 归入同一个文件。

---

<!--原文-->
> ## File format
> 
> The file should be written in a relaxed, readable style, more like a short design document than a database entry. Use paragraphs, code samples, and examples to make the reasoning clear and useful to someone encountering it for the first time.

<!--翻译-->
> ## 文件格式
>
> 文件应以轻松可读的风格编写，更接近简短设计文档而非数据库条目。使用段落、代码示例和示例来使推理清晰，对首次接触的人有用。

---

<!--原文-->
> ### Naming the file
> 
> Use a short, descriptive kebab-case name for the concept: `dark-mode.md`, `plugin-system.md`, `graphql-api.md`. The name should be recognizable enough that someone browsing the directory understands what was rejected without opening the file.

<!--翻译-->
> ### 文件命名
>
> 为概念使用简短、描述性的 kebab-case 名称：`dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名称应足够易识别，使浏览目录的人无需打开文件就能理解被拒绝的内容。

---

<!--原文-->
> ### Writing the reason
> 
> The reason should be substantive: not "we don't want this" but why. Good reasons reference:
> 
> - Project scope or philosophy ("This project focuses on X; theming is a downstream concern")
> - Technical constraints ("Supporting this would require Y, which conflicts with our Z architecture")
> - Strategic decisions ("We chose to use A instead of B because...")
> 
> The reason should be durable. Avoid referencing temporary circumstances ("we're too busy right now"); those aren't real rejections, they're deferrals.

<!--翻译-->
> ### 编写理由
>
> 理由应有实质内容：不是"我们不想要这个"，而是为什么。好的理由引用：
>
> - 项目范围或哲学（"本项目专注于 X；主题化是下游关注的问题"）
> - 技术约束（"支持此功能需要 Y，这与我们的 Z 架构冲突"）
> - 战略决策（"我们选择使用 A 而非 B，因为...）
>
> 理由应是持久的。避免引用临时情况（"我们现在太忙了"）；那些不是真正的拒绝，而是推迟。

---

<!--原文-->
> ## When to check `.out-of-scope/`
> 
> During triage (Step 1: Gather context), read all files in `.out-of-scope/`. When evaluating a new issue:
> 
> - Check if the request matches an existing out-of-scope concept
> - Matching is by concept similarity, not keyword: "night theme" matches `dark-mode.md`
> - If there's a match, surface it to the maintainer: "This is similar to `.out-of-scope/dark-mode.md`. We rejected this before because [reason]. Do you still feel the same way?"
> 
> The maintainer may:
> 
> - **Confirm**: the new issue gets added to the existing file's "Prior requests" list, then closed
> - **Reconsider**: the out-of-scope file gets deleted or updated, and the issue proceeds through normal triage
> - **Disagree**: the issues are related but distinct, proceed with normal triage

<!--翻译-->
> ## 何时检查 `.out-of-scope/`
>
> 在分诊期间（步骤 1：收集上下文），读取 `.out-of-scope/` 中的所有文件。评估新 Issue 时：
>
> - 检查请求是否匹配现有的 out-of-scope 概念
> - 匹配依据概念相似度而非关键词："night theme" 匹配 `dark-mode.md`
> - 如果匹配，向维护者呈现："这与 `.out-of-scope/dark-mode.md` 类似。我们之前因 [原因] 拒绝了此请求。您仍然持相同看法吗？"
>
> 维护者可能：
>
> - **确认**：新 Issue 被添加到现有文件的"先前请求"列表中，然后关闭
> - **重新考虑**：out-of-scope 文件被删除或更新，Issue 进入正常分诊流程
> - **不认同**：Issue 虽相关但不同，进入正常分诊流程

---

<!--原文-->
> ## When to write to `.out-of-scope/`
> 
> Only when an **enhancement** (not a bug) is *rejected* as `wontfix`. This applies to enhancement PRs exactly as it does to issues: a rejected PR is recorded here so the same request doesn't return as fresh code.
> 
> Do **not** write here when something is closed as `wontfix` because it's **already implemented**. That's a built feature, not a rejected one; recording it would poison the dedup checks with false rejections. Instead, the closing comment points to where the feature already lives.

<!--翻译-->
> ## 何时写入 `.out-of-scope/`
>
> 仅当**enhancement**（非 bug）被*拒绝*为 `wontfix` 时。这同样适用于 enhancement PR：被拒绝的 PR 记录在此，以便相同的请求不会以新代码的形式再次出现。
>
> **不要**在因某功能**已实现**而关闭为 `wontfix` 时写入这里。那是已构建的功能，不是被拒绝的功能；记录它会导致去重检查出现误判。相反，关闭评论应指向该功能已存在的位置。

---

<!--原文-->
> The flow:
> 
> 1. Maintainer decides a feature request is out of scope
> 2. Check if a matching `.out-of-scope/` file already exists
> 3. If yes: append the new issue to the "Prior requests" list
> 4. If no: create a new file with the concept name, decision, reason, and first prior request
> 5. Post a comment on the issue explaining the decision and mentioning the `.out-of-scope/` file
> 6. Close the issue with the `wontfix` label

<!--翻译-->
> 流程：
>
> 1. 维护者决定某个功能请求超出范围
> 2. 检查是否已存在匹配的 `.out-of-scope/` 文件
> 3. 如果有：将新 Issue 追加到"先前请求"列表中
> 4. 如果没有：创建新文件，包含概念名称、决策、理由和首个先前请求
> 5. 在 Issue 上发布评论，解释决策并提及 `.out-of-scope/` 文件
> 6. 以 `wontfix` 标签关闭 Issue

---

<!--原文-->
> ## Updating or removing out-of-scope files
> 
> If the maintainer changes their mind about a previously rejected concept:
> 
> - Delete the `.out-of-scope/` file
> - The skill does not need to reopen old issues; they're historical records
> - The new issue that triggered the reconsideration proceeds through normal triage

<!--翻译-->
> ## 更新或删除 out-of-scope 文件
>
> 如果维护者对先前拒绝的概念改变主意：
>
> - 删除 `.out-of-scope/` 文件
> - 该技能无需重新打开旧 Issue；它们是历史记录
> - 触发重新考虑的新 Issue 进入正常分诊流程

## AGENT-BRIEF.md 原文与翻译

<!--原文-->
> # Writing Agent Briefs
> 
> An agent brief is a structured comment posted on a GitHub issue or PR when it moves to `ready-for-agent`. It is the authoritative specification that an AFK agent will work from. The original body and discussion are context: the agent brief is the contract.

<!--翻译-->
> # 编写 Agent Brief
>
> Agent Brief 是当 Issue 或 PR 移动到 `ready-for-agent` 时发布在 GitHub Issue 或 PR 上的结构化评论。它是 AFK Agent 工作的权威规格说明。原始正文和讨论是上下文：Agent Brief 是契约。

---

<!--原文-->
> The brief states **what the agent should do**, which stretches to both surfaces: for an issue, that's building the change from nothing; for a PR, it's what's left to do *to the existing diff*: finish it, close gaps, address review points. Same principles either way; the PR example below shows the difference.

<!--翻译-->
> Brief 陈述**Agent 应该做什么**，这适用于两种场景：对于 Issue，是从零开始构建变更；对于 PR，是对*现有 diff* 还需完成的工作：完成它、填补空白、处理审查意见。无论哪种情况都适用相同原则；下方的 PR 示例展示了差异。

---

<!--原文-->
> ## Principles

<!--翻译-->
> ## 原则

---

<!--原文-->
> ### Durability over precision
> 
> The issue may sit in `ready-for-agent` for days or weeks. The codebase will change in the meantime. Write the brief so it stays useful even as files are renamed, moved, or refactored.
> 
> - **Do** describe interfaces, types, and behavioral contracts
> - **Do** name specific types, function signatures, or config shapes that the agent should look for or modify
> - **Don't** reference file paths: they go stale
> - **Don't** reference line numbers
> - **Don't** assume the current implementation structure will remain the same

<!--翻译-->
> ### 持久性优先于精确性
>
> Issue 可能在 `ready-for-agent` 状态停留数天甚至数周，期间代码库会发生变化。编写 Brief 时应确保其在文件被重命名、移动或重构后仍然有用。
>
> - **应该**描述接口、类型和行为契约
> - **应该**命名 Agent 应查找或修改的具体类型、函数签名或配置结构
> - **不应**引用文件路径：它们会过时
> - **不应**引用行号
> - **不应**假设当前的实现结构将保持不变

---

<!--原文-->
> ### Behavioral, not procedural
> 
> Describe **what** the system should do, not **how** to implement it. The agent will explore the codebase fresh and make its own implementation decisions.
> 
> - **Good:** "The `SkillConfig` type should accept an optional `schedule` field of type `CronExpression`"
> - **Bad:** "Open src/types/skill.ts and add a schedule field on line 42"
> - **Good:** "When a user runs `/triage` with no arguments, they should see a summary of issues needing attention"
> - **Bad:** "Add a switch statement in the main handler function"

<!--翻译-->
> ### 行为描述而非过程描述
>
> 描述系统**应该做什么**，而非**如何**实现。Agent 将全新探索代码库并做出自己的实现决策。
>
> - **好的：** "`SkillConfig` 类型应接受一个可选的 `schedule` 字段，类型为 `CronExpression`"
> - **坏的：** "打开 src/types/skill.ts，在第 42 行添加 schedule 字段"
> - **好的：** "当用户不带参数运行 `/triage` 时，他们应看到需要关注的 Issue 摘要"
> - **坏的：** "在主处理函数中添加 switch 语句"

---

<!--原文-->
> ### Complete acceptance criteria
> 
> The agent needs to know when it's done. Every agent brief must have concrete, testable acceptance criteria. Each criterion should be independently verifiable.
> 
> - **Good:** "Running `gh issue list \-\-label needs-triage` returns issues that have been through initial classification"
> - **Bad:** "Triage should work correctly"

<!--翻译-->
> ### 完整的验收标准
>
> Agent 需要知道何时完成。每个 Agent Brief 必须包含具体、可测试的验收标准。每项标准应可独立验证。
>
> - **好的：** "运行 `gh issue list --label needs-triage` 返回已完成初始分类的 Issue"
> - **坏的：** "分诊应正常工作"

---

<!--原文-->
> ### Explicit scope boundaries
> 
> State what is out of scope. This prevents the agent from gold-plating or making assumptions about adjacent features.

<!--翻译-->
> ### 明确的范围边界
>
> 说明不在范围内的内容。这防止 Agent 过度设计或对相邻功能做出假设。

---

<!--翻译-->

> ### 优秀的 Agent Brief（bug）

---

<!--原文-->
> **Category:** bug
> **Summary:** Skill description truncation drops mid-word, producing broken output
> 
> **Current behavior:**
> When a skill description exceeds 1024 characters, it is truncated at exactly
> 1024 characters regardless of word boundaries. This produces descriptions
> that end mid-word (e.g. "Use when the user wants to confi").
> 
> **Desired behavior:**
> Truncation should break at the last word boundary before 1024 characters
> and append "..." to indicate truncation.
> 
> **Key interfaces:**
> - The `SkillMetadata` type's `description` field: no type change needed,
>   but the validation/processing logic that populates it needs to respect
>   word boundaries
> - Any function that reads SKILL.md frontmatter and extracts the description
> 
> **Acceptance criteria:**
> - [ ] Descriptions under 1024 chars are unchanged
> - [ ] Descriptions over 1024 chars are truncated at the last word boundary
>       before 1024 chars
> - [ ] Truncated descriptions end with "..."
> - [ ] The total length including "..." does not exceed 1024 chars
> 
> **Out of scope:**
> - Changing the 1024 char limit itself
> - Multi-line description support

<!--翻译-->
> **分类：** bug
> **摘要：** Skill 描述截断在单词中间断开，产生损坏的输出
>
> **当前行为：**
> 当 Skill 描述超过 1024 个字符时，它在恰好 1024 个字符处截断，不考虑单词边界。这产生的描述在单词中间结束（例如 "Use when the user wants to confi"）。
>
> **期望行为：**
> 截断应在 1024 个字符前的最后一个单词边界处断开，并追加 "..." 以指示截断。
>
> **关键接口：**
> - `SkillMetadata` 类型的 `description` 字段：无需类型变更，但填充它的验证/处理逻辑需要尊重单词边界
> - 任何读取 SKILL.md 前置元数据并提取描述的函数
>
> **验收标准：**
> - [ ] 低于 1024 字符的描述保持不变
